# Architecture and implementation limits

## Runtime shape

The Streamlit dashboard in `src/signal_stack/app.py` calls service modules directly. Services use SQLAlchemy and persistent SQLite. `src/signal_stack/cli.py` supports setup, research, discovery, collection, manual jobs, and the separate scheduler process.

The database stores company-scoped profile attributes, classification snapshots, interviews, sources, crawls, documents, developments, signals, evidence links, verification history, briefs/actions, uploads with structured analysis summaries, source audits, schedules, and job runs. Schema version is 17. Migrations are additive and record each version; tests verify preservation of existing company, document, development, competitor, interview, and onboarding data. Competitor profiles store editable products/services, target market, customer segments, geography, relationship, supporting source URLs and a discovery timestamp; unknown fields stay blank and legacy discovery timestamps stay null. Signal classifier method is persisted separately from downstream analysis method.

## Company context and interview

Company research stores source-stated observations with URL and excerpt provenance. The classifier stores industry, sub-industry, business model, products/services, customer segments, geography, problems, drivers, regulatory context, evidence, uncertainty, confidence, provider, input fingerprint, and timestamp. Deterministic classification uses generic profile evidence, never company-name rules, and leaves unsupported labels unknown. A configured local Ollama model may suggest labels only with profile fields and verbatim quotes that the service checks against stored evidence.

Ten topics cover revenue, segments, customer needs, differentiation, alternatives, market change, risk, growth, internal information, and leadership decisions. Profile changes update unanswered questions while preserving completed answers. Topic-specific follow-ups are based on the answer content. Ollama question generation is optional and validated; errors fall back to deterministic profile questions.

OpenRouter's Perplexity Decider Flash V1.3 free model classifies public-signal type through its Decisions API; this model returns structured decisions, not narrative prose. The Monday brief's separate explicit opt-in uses the free `openai/gpt-oss-120b:free` chat model. It sends the selected company name, up to eight public-source signal excerpts, and source-stated public profile fields. Internal uploads, founder interview answers, and founder-provided profile fields are excluded. Both integrations reject configured model IDs without the `:free` suffix. Synthesis output must be valid JSON, reference a known signal ID, and quote at least 20 characters found in that signal's stored excerpt; unmatched items are discarded. Remaining model implications are labeled as unverified suggestions. Missing keys, provider errors, malformed output, or unmatched citations leave the deterministic report intact. This uses OpenRouter's documented [Chat Completions API](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request?explorer=true); no live provider call is claimed.

## Source and competitor discovery

Discovery produces unapproved candidates from profile-specific public RSS search URLs, evidence-derived industry searches, the official homepage, labeled first-party feed/help/blog links, and an internal-upload source. Each source stores a reason, category, reliability, relevance, health, and review status. Public sources must pass access/robots checks and user review before approval. The source manager supports batch approval only for candidates validated within seven days.

The Company Intelligence Profile page has a separate, optional Tavily Search workflow. It sends the company name and only selected source-stated/assignment-provided public profile fields. It excludes founder interview answers and internal uploads. Each provider result is URL-validated, bounded, deduplicated, and saved as a candidate plus an audit record containing the query, title, excerpt, publication date when supplied, and provider ranking score. The provider score is not factual confidence. Search snippets do not create profile facts, documents, signals, or approvals; a reviewer must inspect and validate the original page, then approve and crawl it through the guarded crawler. `none` is the default provider and returns a visible unavailable state.

Competitor candidates come from explicit comparison text in crawled competitor sources. Customer, supplier, investor, partner, and explicitly negated mentions are filtered conservatively; deduplication uses normalized entity names. When evidence supports it, the app records direct, indirect, substitute, or emerging type, cited excerpt, evidence URL, confidence, rationale, and status. The profile has editable fields for products/services, market, customer segments, geography and relationship, plus supporting URLs. Automatically extracted profile fields remain blank unless evidence supports them. Users can edit candidate details while retaining provenance; duplicate website domains within one company are rejected. This is not a complete competitor search/profile cross-check workflow and does not promise 5–10 candidates.

## Collection and evidence

The collector accepts public HTTP(S) pages and RSS/Atom feeds. It checks resolved IPs are public, pins the connection, validates TLS hostnames, rechecks redirects, observes `robots.txt`, uses timeouts and response-size limits, and paces requests by host. It fails closed when robots rules cannot be read. It does not bypass logins, CAPTCHA, paywalls, or other access restrictions.

Documents retain canonical URL, company/source IDs, event date when explicit, publication date, discovery date, modification date when available, article marker, content hash, and version. HTML metadata dates come from Open Graph/article metadata, standard metadata, JSON-LD, and `<time datetime>`. RSS/Atom publication and update dates remain distinct. Unknown dates stay null.

Homepage snapshots are baselines. Repeated URL/content pairs update `last_seen_at`; unchanged recrawls do not create signals. Changed page content creates a new retained version, and a meaningful non-homepage change can create a signal even when publication time is unknown. Ordinary homepage, navigation, and footer changes do not become developments. Duplicate evidence at another URL retains provenance without duplicating the signal.

## Analysis, ranking, and briefs

Every development stores source-reported wording separately from interpretation and recommendation, plus affected business area, analysis confidence/rationale/method, and verification status. `services/analysis_pipeline.py` separates event extraction, company-impact assessment, recommendation generation, and interpretation-fit confidence. Company profile and classification context inform the deterministic per-signal interpretation. When relevant profile context is missing, the pipeline says company-specific fit is uncertain and declines to recommend a company-specific action. Analysis confidence describes fit, not factual truth; source reliability and evidence strength remain separate. A single source does not establish independent verification. Optional OpenRouter brief synthesis adds concise leadership framing for public signals only; it does not create signal records or change their type, score, or verification state.

Ranking keeps relevance, impact, urgency, reliability, evidence strength, recency, and novelty separate. Weights are company-scoped and normalized. Saving weights recalculates active signals transactionally from their stored dimensions using the normalized weighted sum; evidence and classifications are unchanged. The intelligence feed defaults to newest-first with deterministic ID tie-breaking; relevance-score and oldest-first orders are explicit options. Unknown publication dates get a modest recency value; future dates are capped with an explanation. Scores support triage and do not verify claims.

Briefs use the ten required headings, cite stored evidence, show publication/event/discovery/modification dates or `Unknown`, and include verification, reliability, evidence strength, analysis confidence/rationale, affected area, and recommended action. The optional LLM summary requires an exact quote match in its signal excerpt, identifies the source and signal ID, and labels implications as suggestions. Crawled and founder-provided text is escaped before storage. Persisted briefs are sanitized again before app rendering/download so old records cannot create headings or executable links. Source URLs are normalized before being included; invalid URLs are omitted. The reporting window uses the company's configured IANA time zone. Empty coverage is called “not assessed.” Saved prior briefs are not edited when new crawls arrive. Markdown and PDF exports are available.

## Internal files and scheduling

CSV uses Python's CSV reader. XLSX is read as ZIP/XML with expansion limits; macros and external links are not executed. PDF uses `pypdf` with an available runtime fallback; TXT must be UTF-8. Uploads are limited to 10 MB and extracted text to 500 KB. Files stay in `data/uploads`, are not sent to OpenRouter, and are treated as evidence only.

The scheduler stores independent weekly and monthly schedules, uses company time zones, prevents overlapping SQLite job claims, records failures/partial runs, and recovers stale running claims. Claim and execution sessions are closed on acquisition, transaction, execution, and commit failures. It polls approved public sources using each company's configured hourly interval (1–720 hours), persists attempts/success/next-due times, leases a source while crawling, and retries failures with bounded exponential backoff. Per-source custom intervals are not implemented. DST tests cover nonexistent and ambiguous local wall times. It runs separately from Streamlit and stops when its process or host stops.

## Security and known limits

Authentication uses a configured PBKDF2-SHA256 password hash, Streamlit's cookie signing secret, an inactivity timeout, and a logout control. In production, SQLAlchemy ORM reads and writes fail without a principal stamped after login; scheduled and CLI processes use explicit system principals. The current account is a single founder/admin with access to every company workspace. This build does not implement multiple accounts, roles, or per-company membership, so it is not a multi-tenant hosted service. Development mode is loopback-only through the provided startup wrapper. Production mode fails closed without both an authentication hash and a session secret. URL and upload safeguards remain necessary. `.env` is git-ignored; `.env.example` contains placeholders only. Database, upload, and report outputs are excluded from Git by `.gitignore`.

`Dockerfile` runs the app as non-root. `compose.yaml` requires production credentials, runs an additive migration step before app/scheduler startup, persists database/upload/report data, keeps the host port loopback-bound, and defines a health check plus bounded log rotation. Direct package dependencies are pinned in `pyproject.toml`; transitive dependencies are not captured in a full lockfile. Docker was not available to build or deploy this configuration.

The local acceptance report is refreshed with a read-only database connection by `scripts/refresh_demo_acceptance_report.py`. The current database has not met the public source, competitor, real intelligence, or substantive report targets. Earlier shell checks could not resolve public DNS or reach PyPI, and no live provider call is claimed. No sample factual reports are manufactured.
